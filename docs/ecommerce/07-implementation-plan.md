# 実装計画・タスク・完了条件

## 実装前に承認が必要な事項

決定済み：Stripe、JPY、税込表示方針、国内＋指定海外地域、国別固定送料、30分在庫予約、初期は単一variant運用、ログインユーザー注文履歴、ゲスト向け期限付き照会リンク、Stripe API全額返金、返品受領・検品後の在庫復元。

公開前の未決事項：

1. 海外配送対象国、各国送料、配送会社、分割発送の要否。
2. 国別税率・徴収義務（専門家確認必須）。税込価格の端数処理は商品明細ごとに四捨五入する方針で決定済み。
3. Stripe本番アカウント、Webhook URL/secret、返金権限・イベント設定。
4. 注文・住所・決済参照・在庫監査の保存期間、アカウント削除/匿名化。
5. メール送信基盤、キュー/Storage/DB/デプロイ/監視の実環境情報。
6. 特定商取引法表示、規約、プライバシー、返品/キャンセル規約の公開内容。

税・配送設定のない国ではチェックアウトを有効にしない。

## フェーズ

### Phase 0：現況・業務条件の確認

**タスク**

- 本番を含む接続環境、migration適用状況、MySQLバージョン、現在のStripeクレジットWebhook構成を、許可を得た読み取り手順で確認。
- 商品データ、SKU規則、在庫管理主体、出荷担当、返品/返金、税/送料、注文問合せ、保存期間を合意。
- 決済事業者のWebhook/Checkout仕様、テスト環境、成功/失敗/期限切れ状態を確認。
- 本設計のER、状態機械、画面、リリース受入条件を承認。

**完了条件**

- 未確定事項に決定者・結論・保留期限が記録され、P0実装範囲が固定される。
- 既存DBとの差分と追加migrationの影響を説明できる。

実DB/本番環境の調査はこの作業では実施していない。稼働DBへの読み取り権限/接続方法はユーザー側で確認し、接続前に明示承認する。実装テストは明示的にSQLite in-memoryを使い、本番DBへ接続しない。

### Phase 1：ドメイン/DB・認可基盤

**タスク**

- EC商品/variant/category/image/inventory/cart/order/payment/shipment関連のmigrationとモデル/Policyを設計・実装。
- 外部キー、unique、CHECK対応、index、soft delete、注文スナップショットをレビュー。
- 既存Stripe WebhookとEC決済の責任分界を分離。DB transactionでの副作用、event idempotencyを確立。
- 開発/CI用のmigrationとseed/factoryを準備（既存データを破壊しない）。

**テスト**

- schema FK/unique/index、商品とvariant関係、カスケード/NULL化、User削除後の注文保持。
- Admin/Policy認可、guest cart token所有確認。
- migration fresh適用と既存DBからのupgradeを別々に検証。
- 既存認証、タロット、Stripeクレジット購入関連テストの回帰。

**完了条件**

- migration rollback方針、既存データへの影響、backup/restore手順がレビュー済み。
- カード情報や不要な個人情報をDBモデルに含めていない。

### Phase 2：商品管理・公開カタログ

**タスク**

- Admin商品/カテゴリ/variant/画像/在庫編集、販売状態、推薦設定。
- 商品一覧・詳細・検索・カテゴリ絞り込み、画像配信、販売不可商品ガード。
- 在庫調整台帳、画像アップロード検証、アーカイブ方式。

**テスト**

- AdminのみCRUD可能、公開商品だけ検索結果に出る、非公開・アーカイブ・在庫切れの表示。
- SKU重複、負数/不正価格、無効カテゴリ、不正画像形式/巨大画像を拒否。
- 複数画像の順序、差替、削除とStorage失敗時の整合。
- variantが複数ある商品でSKU/価格/在庫が正しく分離される。

**完了条件**

- Adminで商品を公開/停止し、購入可能条件が一覧と詳細に一貫して反映される。

### Phase 3：カート・注文・在庫予約

**タスク**

- ゲスト/ユーザー双方のカート、追加/数量変更/削除、認証時統合方針。
- 注文情報・配送先・確認画面、サーバー側の価格/送料/税計算。
- 注文行スナップショット、注文番号、注文冪等性。
- DBロック/条件付き更新、在庫予約/解除/販売確定台帳、予約期限の運用。

**テスト**

- 価格改ざん、数量上限、非公開化/価格変更/在庫切れ後の注文確認拒否または更新案内。
- 並行購入・二重POST・複数variant同時更新で売越し/デッドロック/二重予約なし。
- 注文時点の商品名/価格/数量/税/送料が後日の商品変更後も保持される。
- 期限切れ、決済失敗相当時の予約解放は一度だけ。
- Guest/userのカート境界とログイン時統合が合意仕様どおり。

**完了条件**

- 在庫1個に対する並行注文テストで予約成功は1件だけ、残高・台帳の計算が一致する。

### Phase 4：決済・Webhook・メール

**タスク**

- 決済provider adapter、Checkout作成/再試行/照合、provider側idempotency。
- Webhook署名検証、イベント許可リスト、金額/通貨照合、冪等イベント台帳、状態遷移。
- 決済returnの「確認中/成功/失敗」画面と注文メールの送信/再試行。
- 返金・キャンセルは合意した範囲のみ実装。

**テスト**

- provider SDKをfake/mockして成功/失敗/timeoutを検証。実カード/本番資格情報は使わない。
- 不正署名、改変、event重複/並行、順不同、金額/通貨/注文ID不一致を拒否/安全処理。
- return URL偽装ではpaidにならない、Webhook前の画面は待機中、Webhook後に正しい状態となる。
- メール失敗時に注文状態を戻さず再試行でき、重複Webhookで同一メールを多重送信しない。
- 既存Stripeクレジット購入Webhookの署名検証・記録・重複動作が維持される。

**完了条件**

- テスト環境で成功/失敗/タイムアウト/再送のend-to-end運用を確認し、照合手順が文書化される。

### Phase 5：配送・占い推薦・法務/運用

**タスク**

- Admin注文一覧/詳細、発送/追跡/出荷状態、送料設定。
- 占い結果生成時の推薦選定、ログイン読取保存、ゲストsession/共有Cache保存、再表示。
- ナビ/Blade画面、法的表示とメール文言、個人情報保持・匿名化。
- ログ・監視・バックアップ・Queue再試行・運用者手順を整備。

**テスト**

- 注文状態遷移、複数shipmentの有無、配送通知、権限、追跡番号/PIIの閲覧。
- 推薦の抽選候補が販売中・在庫あり・フラグONに限定される。
- 同じDB/session/shared readingを再表示して推薦が変わらない。推薦対象なしでも占い画面は正常。
- 商品停止/在庫切れ/削除後も既存占い結果・注文を安全に再表示。
- 既存タロット生成・履歴・共有・登録時移行・日次占いの回帰。
- 各画面のスマートフォン、アクセシビリティ、入力エラー、メール表示を確認。

**完了条件**

- 実運用の担当者が商品公開から注文発送/問合せまで試せる。商取引表示・規約・プライバシー文書が承認済み。

### Phase 6：リリース準備・段階公開

**タスク**

- CIにmigration、静的解析/format、テストを追加し、既存mainlineの失敗基準を決定。
- Stagingの決済Webhook/メール/Storage/Queue/在庫初期値を検証。
- DBバックアップ、復旧、Webhook再送、未決済予約解放、決済/注文照合、事故対応を演習。
- 限定商品/低在庫で段階公開し、在庫・決済・メール・エラーを監視。

**テスト・完了条件**

- rollbackだけで注文/外部決済が失われない移行計画、バックアップからの復元確認、Webhook再処理手順、問い合わせ体制を承認。
- 本番相当環境で決済テストモードの購入から発送までを完了。
- 監視期間の重大な売越し、二重請求、状態不一致、個人情報露出が0件である。

## リリースブロッカー

- 決済の署名検証・重複処理、同時購入在庫テストが未通過。
- 注文金額/送料/税がサーバー再計算されない。
- 注文時点の明細スナップショットがない。
- メール/ログ/共有画面にカード情報や不要な住所等が露出。
- 特商法表示、プライバシー、返品/キャンセル条件が未承認。
- 既存占い・アカウント削除・Stripeクレジット購入の回帰試験が未通過。
