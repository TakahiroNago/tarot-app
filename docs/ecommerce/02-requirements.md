# EC機能要件・非機能要件

## 前提と優先度

本書の`必須候補`は、依頼内容に明記された範囲を示す。価格通貨、課税、配送条件等の未決事項を固定するものではない。P0=初期リリースの成立に必要、P1=初期リリースに必要だが運用合意後に実装、P2=将来候補。

## 機能要件

| ID | 優先度 | 要件 | 主な受入条件 |
|---|---|---|---|
| CAT-01 | P0 | Adminが商品を登録・編集・販売停止/アーカイブできる | 非Adminは拒否。販売済商品・参照中商品を物理削除せず注文履歴を保持 |
| CAT-02 | P0 | 商品に複数画像を設定できる | 形式・容量・件数制限、並び順、主画像、削除/差替を管理 |
| CAT-03 | P0 | カテゴリ管理と商品への複数カテゴリ割当 | 非公開商品は公開一覧・検索に出ない |
| CAT-04 | P0 | 商品価格・SKU・販売状態を管理する | SKU一意。金額は通貨の最小単位整数で保存し、画面入力もサーバー再検証 |
| CAT-05 | P0 | 商品バリエーション拡張を妨げない | 価格/SKU/在庫をvariant単位に置き、単一商品はdefault variantで表現可能 |
| CAT-06 | P0 | 在庫数と変動履歴を管理する | 管理者調整を含む全変動が監査可能。負在庫・二重減算を防止 |
| CAT-07 | P0 | 商品ごとに占い推薦の対象/対象外を設定 | 公開中かつ購入可能在庫がある商品だけ選択候補 |
| SHOP-01 | P0 | 商品一覧・詳細・検索・カテゴリ絞込 | 公開/販売可能商品のみ。入力値を検証しページネーション |
| CART-01 | P0 | ゲスト・ログイン利用者のカート | 数量変更/削除、在庫・販売状態・価格の再検証、ログイン時のカート統合方針 |
| ORDER-01 | P0 | ゲスト購入、連絡先・配送先入力、確認画面 | 注文確定前に商品、数量、送料、税、合計、配送先を確認。サーバー再計算 |
| PAY-01 | P0 | 外部決済サービスへ遷移して支払い、注文完了表示 | カード情報は自社システムに入力・保存しない。戻りURLだけで支払い成功にしない |

| MAIL-01 | P0 | 注文成立後の購入完了メール | 受取人・注文内容が注文スナップショットと一致。送信再試行を考慮し二重送信抑止 |

| REC-02 | P0 | 同じ占い結果の再表示で同じ商品を表示 | 初回選択を保存し再抽選しない。ログインDB、ゲストセッション/共有表示に整合 |
| ORD-01 | P0 | Adminが注文一覧・詳細と状態を確認 | 個人情報を必要権限者のみに表示。状態遷移を許可リスト化 |
| SHIP-01 | P0 | 発送状態、配送会社、追跡番号を管理 | 出荷・配送完了等の操作履歴を残す。複数口配送の要否は要決定 |
| SHIP-02 | P0 | 送料を計算・表示・保存 | 送料ルールをサーバーで適用し、注文時点の金額/ルール結果を保存 |
| REFUND-01 | P0 | Stripe APIによる全額返金と返品後の在庫復元 | 返金完了だけでは在庫を戻さず、返品受領・検品後の管理者操作で台帳記録 |

## 状態の分離

- 商品販売状態：`draft` / `published` / `archived`等。具体的な表示語はUIで決定。
- 在庫状態：入荷総数（on_hand）と予約数（reserved）を区別。販売可能数は`on_hand - reserved`。
- 注文状態：`pending_payment`、`paid`、`processing`、`shipped`、`completed`、`cancelled`、`payment_review`、`refund_pending`、`refunded`。
- 決済状態：`pending`、`paid`、`failed`、`cancelled`、`payment_review`、`refund_pending`、`refund_review`、`refunded`。部分返金は提供せず、検知時は`refund_review`にする。
- 配送状態：`pending`、`shipped`、`delivered`。

注文、決済、配送を単一statusに押し込まない。画面には内部の値を出さず、`App\Support\OrderStatusLabel`の日本語表示を使う。時刻の保存と日付の区切りは`APP_TIMEZONE`に従い、注文画面の表示だけ`APP_DISPLAY_TIMEZONE`（既定は日本時間）に変換する。

## 非機能要件

### セキュリティ・個人情報

- 全書き込みはCSRF保護、サーバー側validationと認可を行う。
- Admin機能は既存`auth`/`active`/`verified`/`admin`を基本にし、必要なら注文PII閲覧を追加制御する。
- 決済カード情報を保存しない。Webhook署名・金額・通貨・対象注文を検証する。
- 住所、氏名、メール、電話、追跡番号はログ、URL、解析イベントに出さない。保存期間と消去/匿名化を決める。
- 共有URLに注文情報・アカウントID・配送先を含めない。

### 整合性・可用性

- 同一SKU同時購入でも売越ししない。注文行、在庫残高、在庫台帳を一トランザクションで更新し、DB制約を併用。
- Webhook再送、決済画面の再読込、二重クリック、メール再試行を冪等にする。
- 外部決済やメールが停止しても注文・在庫状態を照合し、回復可能な処理履歴を残す。
- タロット推薦の商品検索・表示が失敗しても占い結果自体は正常表示できる。

### 性能・運用

- 商品一覧・注文一覧はページネーション。検索はindex設計と上限を設ける。
- 画像は許可形式、サイズ、寸法、枚数に制限し、縮小/配信方法を運用決定。
- 完了メールや重い画像処理はキュー候補。キュー/失敗ジョブ監視・再処理手順を運用環境で確認。
- 注文/在庫/決済の不整合を検知する監視・日次照合を設計する。
- 対応ブラウザー、アクセシビリティ目標、稼働率・応答時間・RPO/RTOは別途合意する。

## 範囲外または未決定

決定済み：Stripe、JPY、税込表示方針、商品明細ごとの税込税額を1円未満四捨五入、初期リリースは日本国内のみ（海外配送は行わない）、地域別固定送料、30分在庫予約、ログインユーザーの注文履歴、ゲスト向け期限付き署名照会リンク、全額返金をStripe API経由で行う方針、返品受領後の在庫復元。

未決定：国内の送料額、税率/徴収義務、Stripeの本番アカウントとWebhook設定、注文/住所/決済参照/在庫監査の保存期間、返品条件・法務文言、メール送信基盤、在庫棚卸し・倉庫数、クーポン。

税額は税込の各商品明細額から税率を逆算し、明細ごとに四捨五入する。送料の課税有無は国別税設定で明示する。税率・徴収義務は専門家確認後に設定し、未設定または重複する国の注文は拒否する。

国・送料・税のルールが未設定の宛先では注文を確定できないようにする。適用税ルールも未設定ならチェックアウトを止め、推測した税率で販売しない。

## 受入の最低条件

1. 公開商品だけが購入でき、商品・送料・税をブラウザーから改ざんできない。
2. 在庫1個への並行購入は最大1注文しか予約/購入できない。
3. 同一Webhookを複数回処理しても決済・注文・在庫・メールの副作用が重複しない。
4. 商品名/価格変更後も既存注文に当時の明細が表示される。
5. ECテストと既存占い・認証・Stripeクレジットテストが両方通る。
6. タロット推薦対象外、対象商品の在庫切れ、候補商品なしでも占い結果は正常に閲覧できる。
