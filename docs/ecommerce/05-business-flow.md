# 商品購入・決済・在庫・配送フロー

## 1. 商品公開・在庫登録

1. Adminが商品、カテゴリ、標準variant（SKU/JPY価格/在庫）、画像、販売状態、占い推薦対象フラグを登録する。初期画面は単一variantで運用するが、データモデルは複数variantを許容する。
2. SKUの一意性、価格の範囲、画像形式/容量、カテゴリの公開状態を検証。
3. 初期在庫は台帳付き調整として記録する。商品一覧には公開済みで販売可能なvariantがある商品だけ表示する。
4. 商品削除要求は原則アーカイブに置き換える。注文・推薦・在庫移動を参照するデータは物理削除しない。

## 2. 占い商品推薦

1. 占い結果の初回表示時に、`reading_recommendable`が有効で、商品が公開中、少なくとも1つ購入可能なvariantの在庫がある商品を候補にする。
2. 候補商品1件を選択し、占い結果に関連付けて保存する。ログイン利用者は`tarot_reading_product_recommendations`へ記録し、ゲストはsession readingと共有Cacheに商品識別子を保持する。
3. 履歴/詳細/共有の再表示では保存済みの商品を再利用し、抽選をやり直さない。
4. 選択後に商品が非公開/削除済みになった場合も同じ商品名と購入不可の注記を表示し、リンクは出さない。在庫切れは商品詳細で示す。推薦表示が失敗しても占い結果の表示・共有は継続する。

選定後すぐに在庫がなくなる競合は許容し、カート/注文確認で再検証する。推薦表示は在庫確保を意味しない。

## 3. カート・注文確認

1. ゲストは推測困難なtokenに紐づくカートを利用し、DBにはtokenそのものではなくhashを保存する案。ログイン時は本人のカートだけを読み、ゲストカート統合ルールは要決定。
2. カート行にはvariantと数量を保持する。クライアントから送られる価格・合計は信用しない。
3. 購入者が連絡先、配送先、配送方法を入力し、注文内容を確認する。初期はJPY決済とし、配送先は有効な国別送料ルールがある国に限定する。
4. サーバーが商品状態、SKU、価格、通貨、数量、販売可能在庫、送料、国別税ルールを再計算。税込税額は商品明細ごとに逆算して1円未満を四捨五入し、送料は国別設定に従って課税する。国/送料/税ルールが未設定または重複、金額変動、在庫不足時は確定を止める。
5. 同一ユーザー/ゲストの二重クリックには注文作成用のidempotency keyを使う。注文番号は推測困難な値とし、逐次DB IDを公開しない。

## 4. 在庫予約と外部決済

注文作成と予約は単一DBトランザクションにする。

1. 対象variantの在庫残高を安定した順序でロック（または条件付きUPDATE）する。
2. `on_hand - reserved >= quantity`を満たすことを確認し、満たさない場合は注文を作らずに中断。
3. 注文と商品/価格/配送/税のスナップショットを保存し、予約在庫を増やして一意の在庫台帳イベントを記録する。
4. `pending_payment`の注文と期限付き予約を作成。
5. DBトランザクションの外で決済providerにCheckout/Payment Sessionを要求。注文ID等の照合用metadataとprovider idempotency keyを設定する。
6. providerへの接続失敗時は注文を失敗/キャンセルへ遷移させ、予約を一度だけ解放する。処理境界をoutbox/再試行可能な状態遷移で設計する。

外部API呼び出しをDBトランザクション内で保持しない。providerのタイムアウト後に成功/失敗が不明な場合、安易に予約を解放せず照合処理を行う。

## 5. Webhook・決済状態

1. Webhook受信時にraw bodyと署名ヘッダーから署名・timestamp等を検証する。無効イベントは拒否。
2. event IDを一意キーとして記録/ロックし、重複イベントは副作用なしで成功応答する。
3. EC専用イベント台帳でevent typeを許可リスト処理し、外部checkout/payment ID、注文参照、金額、通貨、支払状態を照合する。既存のStripeクレジット用Webhook/台帳とは分離する。
4. 決済成功時は注文が有効な予約中であることを確認し、決済・注文状態を更新。予約分を販売確定へ振り替え、on_handを減らしreservedを減らし、台帳記録を一回だけ書く。
5. 失敗・checkout期限切れは注文状態を更新し予約を一度だけ解放。予約解放後に支払成功が届いた場合は他注文の予約在庫を消費せず、`payment_review`にして管理者確認を要する。
6. 返金は別の状態遷移と台帳イベントとして記録し、返金時に在庫を自動復元するかは返品受領後に限定するかを決める。
7. 予期しないイベント、金額不一致、孤立したprovider IDは成功処理にせず、ログ/アラートと再照合キューへ送る。

既存の`stripe_webhook_events`はStripeクレジット機能専用として維持し、ECは`ec_payment_webhook_events`と独立した署名検証エンドポイントを使う。

## 6. 注文メール・注文照会

- 注文・支払状態の確定後にメールをキュー投入する案。送信の一意キー/送信状態を設計し、Webhook再送やQueue再試行で同一完了メールが重複しないようにする。
- メール本文は注文時点の明細、注文番号、決済状態、配送先/注文照会方法を必要範囲だけ表示。カード情報・内部IDは出さない。
- ログイン購入者には所有する注文履歴を提供する。ゲスト注文照会は30日間の期限付き署名リンクで提供し、署名のhashのみをDBに保存する。メール本文に配送先や決済詳細を過度に含めない。

## 事業側の選択済み条件

- Stripe Checkoutを利用する。カード情報をアプリへ保存しない。
- 在庫予約は決済開始から30分を目標とし、Stripe側Checkoutの最低有効期限制約を考慮した短い安全余裕を持たせる。Webhookと期限切れ処理の競合では、予約解除後の遅延決済を管理者確認へ回す。
- 返金はStripe APIによる全額返金を初期対象とする。返品受領・検品後に在庫を別操作で復元する。返金前取消の扱いは業務ルールを確定する。
- 初期リリースでは部分返金を行わない。Stripeダッシュボードからも部分返金を操作しない。誤って部分返金が発生した場合、注文は`refund_review`となり管理者へ通知されるため、残額もStripeで返金して全額返金として完了させる。
- JPYの税込価格を表示する。国別の税ルールは専門家確認後に設定し、設定前に該当国で販売しない。
- 配送先は日本と後日指定される海外地域。国ごとの固定送料を設定し、未設定地域を拒否する。

## 7. 発送・追跡

1. Adminが支払済み注文を確認し、出荷準備/発送へ状態遷移。
2. 配送方法、配送会社、追跡番号、発送日時をshipmentへ記録。
3. 追跡番号登録と発送通知メールを行う。発送前のキャンセル/返金は在庫・決済状態と整合を取る。
4. 配送完了、返送、配送事故は運用ルールに沿って記録。外部配送会社APIは要件確定後に判断する。

## 8. 在庫調整・照合

- 入荷/棚卸し/破損/返品の在庫変更は操作者、理由、関連注文、変更量を台帳に記録。
- 日次または定期ジョブで、在庫残高と台帳合計、期限切れ予約、支払成功・注文未確定の不整合を検出。
- 自動解決できない差分は在庫を黙って変更せず、管理者へ通知し、手動補正を監査ログに残す。

## 異常時の重要ケース

| ケース | 期待挙動 |
|---|---|
| 同一SKU在庫1に同時に複数注文 | ロック/条件更新により一件だけ予約可能 |
| 決済Webhookが重複 | 決済・在庫・注文メールの副作用は一度だけ |
| 決済成功Webhookが画面returnより先 | 完了画面はDB状態を表示 |
| 画面returnがWebhookより先 | 「確認中」とし、後続照会で状態を更新 |
| Webhookが順不同/失敗 | 状態を後戻りさせず、イベントIDと許可遷移で処理 |
| provider成功後にアプリが応答前停止 | 同じprovider idempotency keyで照合/再試行 |
| 期限切れ予約と決済成功が競合 | 競合をトランザクションで解決し、曖昧な場合は自動取消せず照合 |
| メール送信失敗 | 注文は支払済みを維持し、メールだけ再試行可能 |
| 商品価格がカート投入後に変更 | 注文確認で再計算し、変更を購入者に提示 |
