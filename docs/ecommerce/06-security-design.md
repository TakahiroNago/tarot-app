# セキュリティ設計

## 脅威境界

守る資産は注文、連絡先・配送先、決済参照、在庫、Admin操作記録、ゲストカートtoken、既存ユーザー/タロット情報である。ブラウザー入力、URL、外部決済return、Webhook、アップロードファイルはすべて未信頼入力として扱う。

## 認証・認可

- 公開商品閲覧とゲスト購入は未認証で可能とする。ログイン利用者の注文照会は注文所有者と一致すること。
- 商品、カテゴリ、送料、在庫、注文、発送、返金などの管理操作は既存`auth`、`active`、`verified`、`admin` middlewareを適用する。
- ControllerだけでなくPolicy/認可サービス等で対象注文・カートの所有権を検証し、IDORを防ぐ。
- Adminは最小権限を基本とする。注文の住所閲覧、在庫調整、返金などの役割分割が必要か要検討。重大操作に操作者・時刻・理由を残す。
- 管理者以外がrequestの`role`、`is_active`、price、stock、order status、payment statusを直接更新できないよう許可項目を分離。
- ゲストカートはCSPRNG tokenを用い、生tokenはCookie等に限定しDBにはハッシュを保持。Secure/HttpOnly/SameSite属性、失効、ローテーションを設定する。カートID単体を認可に使わない。

## 入力・画面・CSRF

- 全入力をサーバー側で型、長さ、範囲、許可値で検証。検索はORM/parameterized query、HTML出力はBlade escapingを利用する。
- Adminフォーム、カート更新、購入確認、状態変更はCSRF保護する。Webhook以外にCSRF除外を広げない。
- 価格・合計・割引・送料・税・SKU・支払状態はクライアント値を信用せずサーバーで再照会・再計算する。
- 連打/リプレイはidempotency key、DB unique制約、状態遷移で抑制。rate limitはログイン、カート、注文照会、Adminログイン後の危険操作に適用する。
- エラーレスポンスにSQL、ファイルパス、API秘密情報、Webhook raw payload、個人情報を出さない。

## 決済

- Hosted Checkout等、カード情報が当アプリのサーバー/ログを通過しない方式を優先。カード番号、CVC、磁気情報は自社DB、ログ、セッション、メールに保存しない。
- 秘密鍵とWebhook signing secretは環境変数/Secret Managerで管理し、ソースや公開設定に置かない。権限最小化、ローテーション、環境別分離を行う。
- Webhookはraw bodyを使った公式署名検証を行い、失敗時は処理しない。署名timestamp/再送耐性もprovider仕様に合わせる。
- Webhookでevent ID、event type、対象注文、外部決済ID、金額、通貨、expected stateを照合する。ブラウザーreturnだけでpaidにしない。
- イベントID、provider payment ID、注文作成key、在庫台帳keyのunique制約とトランザクションで冪等化。並行再送のunique競合は正常な重複として扱い、予期しないDBエラーと区別する。
- 保存する決済情報はprovider名、参照ID、状態、金額、通貨、時刻等の最小限。provider応答/raw payloadを無制限に保存しない。

## 在庫・注文整合性

- 在庫確保はDB行ロックまたは原子的な条件付きUPDATEで実施し、キャッシュロックのみを根拠にしない。
- 商品/variantのロック順序を一定にし、注文・決済・在庫残高・在庫台帳を短いDBトランザクションにまとめる。
- `on_hand >= reserved >= 0`、予約/販売/返金イベントの整合をDB制約とサービス検証で担保。
- 注文状態と支払状態は別々に管理し、許可された状態遷移だけ行う。再送・順不同イベントで`paid`から`pending`へ戻さない。
- 在庫予約期限処理、Webhook、返金、手動Admin調整の競合をテストする。管理調整は理由・操作者付きの新規台帳行を追加し、過去履歴を書き換えない。

## 個人情報・データ保護

- 注文連絡先/配送先は発送・問い合わせ・法令対応に必要な範囲だけ収集。自由入力項目を増やさない。
- HTTPS、適切なCookie属性、CSRF保護、アクセス制御、DBバックアップ暗号化、Storage権限管理を本番で確認。
- 個人情報はログ、Analytics、例外通知、URL、商品推薦Cacheに含めない。メール宛先、住所、追跡番号をアプリログへ出さない。
- セッションは注文状態の正本にしない。注文住所の暗号化（Laravel encryption等）を採用する場合は検索要件、鍵管理、ローテーション、復旧を設計する。
- User削除時のEC注文保持、匿名化、削除請求、会計/法令上の保存期間、バックアップからの消去方針を法務・事業で定義する。
- ゲスト注文照会tokenは推測不能・期限付き・失効可能とし、アクセス時に必要な追加確認や試行制限を設ける。

## 画像アップロード・Storage

- 許可MIMEと実ファイル内容の両方、拡張子、容量、寸法、画像枚数を検証。SVG等の能動コンテンツは原則許可しない。
- ファイル名をサーバー生成し、パス traversal、二重拡張子、過大画像、画像デコーダ攻撃を防ぐ。必要なら再エンコード/メタデータ除去を行う。
- private/public diskの配置、CDN、アクセスURL、削除/差替時の孤立ファイル清掃とバックアップを決める。注文履歴を商品画像参照だけに依存させない。

## 管理運用・監査

- Admin MFAの有無、ログインrate limit、特権アカウント棚卸しを確認。
- 在庫調整、注文状態、追跡番号、返金/取消、商品公開状態の変更者・日時・対象・理由を監査。
- Webhook失敗、イベント重複、金額不一致、決済/在庫不整合、Queue失敗にアラートと再処理手順を用意。
- 本番Secretsをテスト/開発へ流用しない。デプロイ前にバックアップ、migration rollback、サポート窓口、障害時の決済照合手順を確認。

## セキュリティテスト

- ゲスト/別ユーザーによる他人のカート・注文・配送先・注文照会へのアクセス拒否。
- 非Adminによる全Admin CRUD/在庫/配送/返金操作拒否、停止ユーザー拒否、未確認ユーザーの想定導線。
- CSRF、入力制限、HTML/XSS文字列、検索SQL注入文字列、ファイル偽装/容量超過の安全な拒否。
- 無効署名/欠落署名/古い署名/改変payload/金額・通貨不一致Webhook拒否。
- 同一eventの同時・逐次再送、順不同イベント、決済return偽装、provider応答タイムアウトで状態が重複/逆行しない。
- 同一在庫への並行注文で売越しゼロ、予約の期限切れと支払成功競合で二重解除/減算しない。
- ログ・メール・例外画面・共有画面にカード情報や不要な個人情報が漏れない。
